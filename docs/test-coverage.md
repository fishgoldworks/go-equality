# Test coverage map

This guide shows what each test group checks. The [README development section](../README.md#development) describes setup and validation commands; [package.json](../package.json) defines the commands. Test counts and coverage percentages come from the current run rather than a saved report.

The [independent reference implementation (oracle)](../test/helpers/oracle.js) checks small graphs by enumerating object pairs and possible assignments. It does not reuse the production matcher. Tests cover all small matching patterns and reproducible generated graphs, including ambiguous assignments where equality is not transitive. Comparisons with other libraries are limited to inputs for which both libraries use the same rules.

The [Buffer hook regressions](../test/buffer-hooks.test.js) combine native Buffers with own properties, numeric customisers, heterogeneous collections and deliberate application hooks. VM consumers supply the trusted host `Buffer` before loading the comparator. The [Buffer identity regressions](../test/buffer-identity.test.js) separately check that application hooks are preserved without a `Buffer` global, even when the class has Buffer-like metadata.

[Release-tool tests](../scripts/test-release.js) protect fresh packing, recorded SHA-256 digests, reuse of supplied archives and rejection of missing tarballs. [Development-tool tests](../scripts/test-tooling.js) exercise supported module inputs, child-process failures and consumer cleanup. They check original and cleanup errors together, remaining cleanup attempts and bundle-test discovery failures.

`verify` creates one candidate and tests its installed contents on exact Node 8.0.0 and modern Node; `verify:all` sends the same archive to the real-browser harness. The CommonJS minimum is checked with consumer regressions, separately from the modern Node test runner and its coverage. Default and named ES module imports are checked at the supported version boundaries and on modern Node; [CI](../.github/workflows/ci.yml) owns the configured runtime matrix.

[Defensive-state tests](../test/defensive-state.test.js) check that a previously rejected pair cannot become a required match, buffer lengths are rechecked after type detection, and the library loads without the optional `SharedArrayBuffer` global. The first case uses the internal comparison context directly. The other cases run through the selected source, bundle, or installed API. The buffer-resize case protects a safeguard; callers must still keep inputs unchanged during comparison.

`npm run coverage` requires 100% executable source-line, branch and function coverage, measured separately on the modern supported contributor runtimes. A drop below any threshold fails verification. The README coverage badge shows the source-line measure; it does not claim branch coverage or exhaustive behaviour. Node 8 consumer regressions are compatibility checks, not a separate 100% coverage claim.

Public API documentation coverage is 100%: every exported function and attached method has a checked reference section. There are no public constants. The generator checks that inventory and the executable documentation tests assert example results and expected errors using `// =>` comments. This measure does not mean every behaviour or example variant is tested.

Node VM loader checks cannot test real-browser behaviour such as `document.all`. See [CI](../.github/workflows/ci.yml) for the configured environments and each run's output for its results.

[Optional-capability tests](../test/optional-capabilities.test.js) remove constructors and members before fresh source, focused-source, installed-package and bundle loads, including minified CommonJS/global/AMD output. Native-present controls and independent/combined absences protect callback identity, errors, native payloads and unsupported-operation behaviour. Installed checks repeat these scenarios on each selected real Node runtime and remove capabilities before loading a fresh consumer with supported static ES module imports. See [how these checks run](development.md#optional-capability-checks) for their scope and limitations.

## Test-infrastructure regressions

[Example instrumentation](../test/instrumentExample.test.js) protects sequence-expression grouping, nested assertion insertion and rejection of unsupported explicit result annotations. [Documentation helper tests](../test/documentation-helpers.test.js) check standalone fence extraction, ignored fenced links/headings and false-result controls. [Infrastructure tests](../test/test-infrastructure.test.js) distinguish CommonJS/global/AMD selection, reject invalid selectors, prove main-runner failure/argument propagation and check the independent oracle against manually specified controls.

These test the verification machinery; they are not new equality capabilities or additional generated graph scenarios. No current documentation example is claimed incorrect merely because a checker defect was found. The supported executable-example format is described in the [development guide](development.md#executable-examples-and-test-selection).

## Interpreting results

Most tests use public exports. A few test internal rules directly where a public call would not reach the case. Running the same suite against a bundle or installed package checks that distribution; it does not add new input scenarios.

TypeScript tests check valid calls, reject invalid calls, and confirm that comparisons do not narrow TypeScript types. They check unannotated callback-body and factory-result inference, receiver requirements, and bound/wrapped callback controls. Executed CommonJS and ES module fixtures verify the bound and unbound-receiver conventions through package-name imports. They also check that strict and loose functions have no custom/create methods. Both compilation stages use ES2017 library definitions, `skipLibCheck: false` and no automatic `@types` packages. A tooling regression checks that valid consumers pass and declarations referring to browser or contributor-only globals fail. TypeScript is pinned as a development dependency; it is not required at runtime. Runtime tests separately check what the functions do.

Memory checks limit parts of the V8 heap, not total process memory. Timing benchmarks have no pass/fail speed threshold. Keep the [supported-input limits](API.md#errors-and-supported-inputs) in mind when interpreting failures or adding tests.
